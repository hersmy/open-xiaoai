# Bilibili 指定视频代码点播

延续明确音乐命令走代码的设计：明确的 B 站 BV 号/链接或标题不调用 Agent，公共 HTTP 查元数据，
再以官方 Mac 客户端原生 bilipc URL 打开视频。不使用 computer use、浏览器点击或视频下载，
不读取用户 Cookie、App 存储或 Harness 凭据；代码搜索使用 B 站公开生成的匿名 buvid3，仅在内存缓存。

本机官方客户端 1.17.6 注册 bilipc scheme；通过只读检查其本机代码确认真正路径为
bilipc://page/player?type=ugc&bvid=...&aid=...&cid=...，不是手机 bilibili:// 或桌面 bilipc://video。
已将用户给定 BV18V4i6WEje 的三个标识传入，用户确认打开并播放了正确视频。
探索过程中读取的 App 源码/解码脚本仅在被忽略的本机 .runtime，验证后已清理，不提交或修改 App。

明确“在B站播放标题”“播放B站的标题”“播放视频标题”及指定 BV/常规视频链接走本地分流。
标题先精确匹配，或足够长且仅有一个包含匹配的结果；多个结果时要求 BV，不盲目取第一条。
标题中的逗号/怎么不视为复杂指令，真正的推荐/复合操作继续 Agent。BV 可直接跳过搜索查详情。
只验证普通 UGC 第一分 P；非第一分 P 不擅自当第一集播放，短链/番剧等未接入。

bridge 共享收到/已完成和 AIVS/PNS 恢复逻辑，新增 local_video 路由和 video_* 阶段计时；
原生迟到播放守卫保留。视频轻量动作写自有 .runtime/video-actions.jsonl，不写 Harness 内部会话。
系统 open 成功是请求被接受；没有实际播放验证不能宣称已经出声。本次仅接搜索点播，音乐控制仍操作网易云。

验证包括普通音乐不误路由、明确视频不进 Agent、链接/BV 校验与去跟踪参数、标题消歧、不误播搜索第一项、
HTTP/接口/客户端失败、原生 URL 参数、完整后台入口与用户现场播放确认；只重载本桥接。
